### 核心数据流（一笔跨域认证为例）

```
① 域管理员前端发起请求
    POST /api/cross/request
        ↓ JWT 鉴权
        ↓ 信任策略校验
        ↓ checkOracleForAuth (活跃节点≥门限 + 状态≤600s + score≥70)
    生成 challenge，session.status = PENDING_SIGNATURE
        ↓
② 客户端用 credential 算 sha256(challenge:credential) 提交
    POST /api/cross/verify
        ↓ 服务端重算比对
    session.status = PENDING_APPROVAL
        ↓
③ 管理员审批
    POST /api/cross/approve
        ↓ 二次 checkOracleForAuth
        ↓ 构造 tokenJSON + 算 SHA256 摘要
        ↓ h.Chain.Anchor("cross_auth", requestId, digest)
            ↓ fabric-gateway SubmitAsync
                ↓ Org1 peer endorse
                ↓ Org2 peer endorse
                ↓ orderer Raft 排序
                ↓ 两 peer commit
            ↓ 拿到 TxHash + BlockHeight
        ↓ 写 chain_anchor + audit_log
    session.status = VERIFIED
        ↓
④ 客户端凭 token 调用受保护接口
    POST /api/operations/protected
        ↓ RequireCrossDomainAuth 4 重校验
        ↓ 真实修改 device.RuntimeState
        ↓ Anchor("protected_op", deviceDID, digest)
    返回操作结果 + 链上回执 + 双 Org 背书
```

## 1. 链码 `anchorcc/chaincode.go`（系统唯一智能合约）

**位置**：`fabric/chaincode/anchor-go/chaincode.go`

**职责**：把业务摘要钉在链上账本，提供三个外部方法 + 一个内部 key 生成函数。链上不存原文，只存摘要。

### 1.1 关键代码

```go
type AnchorRecord struct {
    BizType   string  // "cross_auth" / "oracle_report" / "protected_op" / "token_revoke" / "device_register"
    BizRef    string  // 业务唯一标识（RequestID / DeviceDID）
    Digest    string  // 业务原文的 SHA256 摘要
    Timestamp string  // Unix 秒
    CreatedAt string  // RFC3339 时间字符串
}

// 写入：把业务摘要钉到链上
func (s *SmartContract) AnchorRecord(ctx contractapi.TransactionContextInterface,
    bizType, bizRef, digest, ts string) error {
    rec := AnchorRecord{
        BizType: bizType, BizRef: bizRef, Digest: digest,
        Timestamp: ts, CreatedAt: time.Now().UTC().Format(time.RFC3339),
    }
    payload, _ := json.Marshal(rec)
    return ctx.GetStub().PutState(anchorKey(bizType, bizRef), payload)
}

// 反查：按业务键读链上记录
func (s *SmartContract) QueryAnchor(ctx ..., bizType, bizRef string) (*AnchorRecord, error) {
    raw, _ := ctx.GetStub().GetState(anchorKey(bizType, bizRef))
    if raw == nil { return nil, fmt.Errorf("anchor not found") }
    var record AnchorRecord
    json.Unmarshal(raw, &record)
    return &record, nil
}

// 零知识校验：验证方提供 (bizType, bizRef, digest)，链只回答"对/不对"，不返回原文
func (s *SmartContract) VerifyDigest(ctx ..., bizType, bizRef, digest string) (bool, error) {
    record, _ := s.QueryAnchor(ctx, bizType, bizRef)
    return record.Digest == digest, nil
}

func anchorKey(bizType, bizRef string) string {
    return fmt.Sprintf("ANCHOR_%s_%s", bizType, bizRef)
}
```

### 1.2 实现原理
- 链上 state 是 LevelDB（或 CouchDB）KV 存储，key 形如 `ANCHOR_cross_auth_REQ-1234`
- PutState 后只有等区块被 commit、所有 peer 把状态写入本地账本，QueryAnchor 才能读到 — 这是 Fabric "SOV"（Simulate-Order-Validate）模式带来的最终一致性
- `BizType` 是开放扩展的字符串，新增业务类型不需要升级链码
- 不存原文 = ① 隐私保护 ② 节省存储 ③ 提交带宽小→吞吐量高

### 1.3 答辩可能追问
- **「为什么不把整个业务对象上链？」** 物联网设备数据量大、变更频繁，全上链导致链膨胀到 TB 级且共识耗时翻倍；摘要 + 业务库副本是工业界共识做法
- **「VerifyDigest 算"零知识"吗？」** 验证方不需要把原文交给链，链只回答"对/不对"，原文留在客户端本地。这相比"链上明文 + 客户端比对"减少了原文泄漏面

### 2.3 Anchor 方法（写链）

```go
func (s *FabricGatewayService) Anchor(bizType, bizRef, digest string) (AnchorResult, error) {
    _, commit, err := s.contract.SubmitAsync(s.anchorFunc,
        client.WithArguments(bizType, bizRef, digest, fmt.Sprintf("%d", time.Now().Unix())))
    if err != nil { return AnchorResult{}, err }

    status, err := commit.Status()  // 阻塞等待链上 commit 完成
    if !status.Successful {
        return AnchorResult{}, fmt.Errorf("fabric commit failed: code=%v tx=%s",
            status.Code, commit.TransactionID())
    }
    return AnchorResult{
        TxHash:      commit.TransactionID(),
        BlockHeight: status.BlockNumber,
    }, nil
}
```

### 2.4 SubmitAsync 内部时序（Fabric SOV 模式）

```
客户端  ──proposal──→  Peer0.Org1 (Simulate + Endorse)  ──→ 拿到签名 1
       ──proposal──→  Peer0.Org2 (Simulate + Endorse)  ──→ 拿到签名 2
       ──tx──────→     Orderer (Raft 共识打包)
                            ↓
       ←──block notify──    Orderer → 各 Peer
                            ↓
       ←──commit status──   Peer 校验 + 写本地账本 → 返回 status
```

### 2.5 ChainInfo / BlockByNumber（读链，走 qscc 系统链码）

```go
func (s *FabricGatewayService) ChainInfo() (*ChainInfo, error) {
```

### 2.6 答辩追问
- **「SubmitAsync 和 Submit 有什么区别？」** SubmitAsync 是 fabric-gateway 1.x 的推荐方式：客户端不等区块 commit 就先拿 proposal response，再单独通过 `commit.Status()` 等待最终状态——可以并行多笔提交
- **「为什么读链要用 qscc 而不是 anchorcc？」** qscc 是 Fabric **自带的系统链码**，专门负责通道/区块/交易元数据查询，不需要部署。anchorcc 是我们自己的业务链码，只懂 anchor 业务

## 3. 多组织背书解析 `endorsements.go`

**位置**：`backend/internal/chain/endorsements.go`

**职责**：从 Fabric protobuf 层层剥洋葱，提取一笔交易的**所有背书者** + **提案发起人**。这是论文创新点"双层信任 / 联盟链可见"的硬证据来源。

### 3.1 数据结构

```go
type EndorserInfo struct {
    MSPID      string  // Org1MSP / Org2MSP
    CommonName string  // peer0.org1.example.com
    Issuer     string  // ca.org1.example.com
    Serial     string  // X.509 证书序列号
    SigShort   string  // 签名前 12 + 后 8 hex
}

type TxParseResult struct {
    ChannelID   string
    HeaderType  string
    TxID        string
    TimestampMs int64
    Creator     *EndorserInfo   // 提案发起者（如 Org1 User1）
    Endorsers   []EndorserInfo  // 所有背书 peer
}
```

### 3.2 解析逻辑（5 层 protobuf 嵌套）

```go
func parseEndorsements(envelope *commonpb.Envelope) (*TxParseResult, error) {
    // Layer 1: Envelope → Payload
    payload := &commonpb.Payload{}
    proto.Unmarshal(envelope.Payload, payload)

    // Layer 2: Payload.Header.ChannelHeader → 通道 / TxID / 时间戳
    ch := &commonpb.ChannelHeader{}
    proto.Unmarshal(payload.Header.ChannelHeader, ch)
    out.ChannelID = ch.ChannelId
    out.TxID = ch.TxId
    out.HeaderType = commonpb.HeaderType_name[ch.Type]
    out.TimestampMs = ch.Timestamp.Seconds*1000 + int64(ch.Timestamp.Nanos)/1e6

    // Layer 3: Payload.Header.SignatureHeader.Creator → 提案发起者
    sigHdr := &commonpb.SignatureHeader{}
    proto.Unmarshal(payload.Header.SignatureHeader, sigHdr)
    out.Creator, _ = decodeIdentity(sigHdr.Creator, nil)

    // Layer 4: Payload.Data → Transaction → Actions
    tx := &peerpb.Transaction{}
    proto.Unmarshal(payload.Data, tx)
    for _, action := range tx.Actions {

        // Layer 5: Action.Payload → ChaincodeActionPayload.Action.Endorsements
        ccap := &peerpb.ChaincodeActionPayload{}
        proto.Unmarshal(action.Payload, ccap)
        for _, end := range ccap.Action.Endorsements {
            info, _ := decodeIdentity(end.Endorser, end.Signature)
            out.Endorsers = append(out.Endorsers, *info)
        }
    }
    return out, nil
}

// 把 msp.SerializedIdentity protobuf 转成 X.509 证书 + 取关键字段
func decodeIdentity(serialized []byte, signature []byte) (*EndorserInfo, error) {
    si := &msppb.SerializedIdentity{}
    proto.Unmarshal(serialized, si)

    info := &EndorserInfo{MSPID: si.Mspid}
    if len(signature) > 0 {
        hexSig := hex.EncodeToString(signature)
        info.SigShort = hexSig[:12] + "..." + hexSig[len(hexSig)-8:]
    }

    block, _ := pem.Decode(si.IdBytes)
    cert, _ := x509.ParseCertificate(block.Bytes)
    info.CommonName = cert.Subject.CommonName
    info.Issuer     = cert.Issuer.CommonName
    info.Serial     = cert.SerialNumber.String()
    return info, nil
}
```

### 3.3 实现原理
- Fabric 把"一笔已签名交易"作为 **protobuf Envelope** 包装：外层是签名 + 内容指纹，内层是业务调用 + 各方背书
- 解析后能拿到：① 谁发起（哪个 Org 的哪个 User）② 哪些 peer 做了 endorse ③ 每个 peer 的真实 X.509 证书信息 + 签名
- 单组织链根本不可能产出多 MSPID 的 Endorsements 数组 — 这就是"联盟链"区别于"中心化数据库 + 哈希戳"的硬证据

### 3.4 答辩追问
- **「能不能伪造背书？」** 不可能。每个 endorser 的签名是用其 MSP 私钥对 proposal hash 签名得到，CA 系统证书链验证 + Fabric 协议层强校验。后端拿到 protobuf 后只是解析展示，不参与签名过程
- **「为什么不直接用 Fabric Gateway SDK 自带的 result.Endorsers？」** SDK 在 SubmitAsync 时返回 `commit.TransactionID()` 不会自动解析背书。要看背书必须 qscc.GetTransactionByID 拉回 ProcessedTransaction 自己解 protobuf

## 4. 跨域门禁中间件 `cross_domain_gate.go`

**位置**：`backend/internal/middleware/cross_domain_gate.go`

**职责**：所有"凭跨域 token 操作目标域资源"的请求都先过这里 4 重校验，任一不过直接 403。

### 4.1 完整代码（精简）

```go
func RequireCrossDomainAuth(db *gorm.DB) gin.HandlerFunc {
    return func(c *gin.Context) {
        deviceDID       := HeaderDecoded(c, "X-Device-DID")          // 源设备
        targetDomain    := HeaderDecoded(c, "X-Target-Domain")       // 目标域
        targetDeviceDID := HeaderDecoded(c, "X-Target-Device-DID")   // 操作对象（可选）

        // ① 必传 header
        if deviceDID == "" || targetDomain == "" {
            c.AbortWithStatusJSON(400, gin.H{"message": "missing X-Device-DID or X-Target-Domain"})
            return
        }

        // ② 数据库存在 VERIFIED session（按 srcDID + toDomain 查）
        var session model.CrossDomainAuthSession
        if err := db.Where("device_d_id = ? AND to_domain_code = ? AND status = ?",
            deviceDID, targetDomain, "VERIFIED").
            Order("verified_at desc").First(&session).Error; err != nil {
            c.AbortWithStatusJSON(403, gin.H{"message": "cross-domain authentication required"})
            return
        }

        // ③ 会话未过期（expiresAt 优先，否则 verifiedAt + 30min 兜底）
        if session.ExpiresAt != nil {
            if time.Now().After(*session.ExpiresAt) {
                c.AbortWithStatusJSON(403, "cross-domain authentication expired"); return
            }
        } else if session.VerifiedAt == nil || time.Since(*session.VerifiedAt) > 30*time.Minute {
            c.AbortWithStatusJSON(403, "cross-domain authentication expired"); return
        }

        // ④ 源设备 ACTIVE
        var srcDevice model.Device
        db.Where("device_d_id = ?", deviceDID).First(&srcDevice)
        if srcDevice.Lifecycle != "ACTIVE" {
            c.AbortWithStatusJSON(403, "device lifecycle is not ACTIVE"); return
        }

        // ⑤ 解析操作对象 DID（优先用 X-Target-Device-DID）
        opDID := deviceDID
        if targetDeviceDID != "" && targetDeviceDID != deviceDID {
            var tgt model.Device
            db.Where("device_d_id = ?", targetDeviceDID).First(&tgt)
            if tgt.DomainCode != targetDomain {
                c.AbortWithStatusJSON(403, "target device not in target domain"); return
            }
            if tgt.Lifecycle != "ACTIVE" {
                c.AbortWithStatusJSON(403, "target device lifecycle is not ACTIVE"); return
            }
            opDID = targetDeviceDID
        }

        c.Set("crossSrcDeviceDid", deviceDID)
        c.Set("crossOpDeviceDid", opDID)
        c.Next()
    }
}
```

### 4.2 双 DID 语义（关键设计）

| Header | 含义 | 谁产生 |
|---|---|---|
| `X-Device-DID` | 源设备 = session.deviceDID（凭证持有方） | 跨域认证发起方 |
| `X-Target-Domain` | 这张 token 解锁的目标域 | 跨域认证目标 |
| `X-Target-Device-DID` | （可选）要操作的**目标域内**设备 | 用户在运维台里选 |

中间件成功放行后，handler 通过 `c.GetString("crossOpDeviceDid")` 拿到真正要操作的 DID，`crossSrcDeviceDid` 用于 session 查找。

### 4.3 答辩追问
- **「为什么要 4 重校验，少一重不行吗？」** 任何一重都拦不同攻击：① 没 header = 缺凭证；② 没 session = 没经过审批；③ 过期 = token 时效；④ 设备失效 = 中途被吊销
- **「为什么把 srcDID 和 opDID 分开？」** 跨域语义是 "A 域的 X 凭通行证去 B 域操作 Y"，两者本质不同。早期实现绑死成同一个，导致"只能操作自己"——退化成单机权限，不是跨域

## 5. 三段式跨域认证（论文核心算法）

**位置**：`backend/internal/api/handlers.go`

**职责**：Request → Verify → Approve 三阶段状态机，每阶段独立鉴权 + 校验。

### 5.1 状态机

```
新创建  ─cross/request──→  PENDING_SIGNATURE
                              │
                          cross/verify
                              │
                              ▼
                         PENDING_APPROVAL
                              │
                         cross/approve
                              ├──→ VERIFIED  (审批通过 + 锚链)
                              └──→ REJECTED  (审批拒绝)
                              
            (管理员任意时刻) cross/revoke
                              ▼
                          REVOKED
```

### 5.2 Stage 1：`RequestCrossDomainAuth`（域管理员发起）

```go
func (h *Handler) RequestCrossDomainAuth(c *gin.Context) {
    var req crossRequestReq
    c.ShouldBindJSON(&req)

    // 1. 检查设备存在 + ACTIVE
    var device model.Device
    h.DB.Where("device_d_id = ?", req.DeviceDID).First(&device)
    if device.Lifecycle != "ACTIVE" {
        response.BadRequest(c, "device not active"); return
    }

    // 2. 检查信任策略（DomainTrustPolicy.enabled）
    if !h.trustPolicyAllows(device.DomainCode, req.ToDomainCode, req.Permission, req.Resource) {
        response.Forbidden(c, "trust policy denied"); return
    }

    // 3. ★ 预言机评分前置校验
    okOracle, reason, detail := h.checkOracleForAuth(device.DeviceDID)
    if !okOracle {
        response.Forbidden(c, "oracle: "+reason)
        return
    }

    // 4. 生成 RequestID + challenge
    requestID := fmt.Sprintf("REQ-%d-%d", time.Now().Unix(), rand.Intn(10000))
    challenge := pkgutil.RandomHex(16)

    // 5. 写 session（PENDING_SIGNATURE）
    session := model.CrossDomainAuthSession{
        RequestID:     requestID,
        DeviceDID:     req.DeviceDID,
        FromDomainCode: device.DomainCode,
        ToDomainCode:  req.ToDomainCode,
        Resource:      req.Resource,
        Permission:    req.Permission,
        TTLSeconds:    req.TTLSeconds,
        Challenge:     challenge,
        Status:        "PENDING_SIGNATURE",
        RequestedBy:   c.GetString("username"),
    }
    h.DB.Create(&session)

    response.OK(c, gin.H{
        "requestId": requestID,
        "challenge": challenge,
        "status":    "PENDING_SIGNATURE",
        "oracle":    detail,
    })
}
```

### 5.3 Stage 2：`VerifyCrossDomainAuth`（签名校验）

```go
func (h *Handler) VerifyCrossDomainAuth(c *gin.Context) {
    var req crossVerifyReq
    c.ShouldBindJSON(&req)

    var session model.CrossDomainAuthSession
    h.DB.Where("request_id = ?", req.RequestID).First(&session)
    if session.Status != "PENDING_SIGNATURE" {
        response.BadRequest(c, "not in PENDING_SIGNATURE state"); return
    }

    // 重算期望签名
    var device model.Device
    h.DB.Where("device_d_id = ?", session.DeviceDID).First(&device)
    expected := sha256Hex(session.Challenge + ":" + device.Credential)
    if req.Signature != expected {
        response.Unauthorized(c, "signature mismatch")
        return
    }

    now := time.Now()
    session.SignatureVerifiedAt = &now
    session.Status = "PENDING_APPROVAL"
    h.DB.Save(&session)

    response.OK(c, gin.H{"status": "PENDING_APPROVAL"})
}

// 签名算法
func sha256Hex(s string) string {
    sum := sha256.Sum256([]byte(s))
    return hex.EncodeToString(sum[:])
}
```

### 5.4 Stage 3：`ApproveCrossDomainAuth`（审批 + 锚链）

```go
func (h *Handler) ApproveCrossDomainAuth(c *gin.Context) {
    var req crossApproveReq
    c.ShouldBindJSON(&req)

    var session model.CrossDomainAuthSession
    h.DB.Where("request_id = ?", req.RequestID).First(&session)

    if !req.Approve {
        session.Status = "REJECTED"; h.DB.Save(&session)
        response.OK(c, gin.H{"status": "REJECTED"}); return
    }

    // ★ 二次预言机校验（防止状态在 Stage1→Stage3 之间恶化）
    okOracle, reason, _ := h.checkOracleForAuth(session.DeviceDID)
    if !okOracle {
        response.Forbidden(c, "oracle re-check failed: "+reason); return
    }

    // 1. 构造 token JSON
    now := time.Now()
    exp := now.Add(time.Duration(session.TTLSeconds) * time.Second)
    tokenObj := gin.H{
        "subject":    session.DeviceDID,
        "fromDomain": session.FromDomainCode,
        "toDomain":   session.ToDomainCode,
        "resource":   session.Resource,
        "permission": session.Permission,
        "issuedAt":   now,
        "expiresAt":  exp,
        "approvedBy": c.GetString("username"),
    }
    tokenJSON, _ := json.Marshal(tokenObj)

    // 2. 算摘要
    digest := sha256Hex(string(tokenJSON))

    // 3. 锚定到 Fabric
    anchor, err := h.Chain.Anchor("cross_auth", session.RequestID, digest)
    if err != nil {
        // 失败时写 audit_log 但不写 session.VERIFIED
        h.auditEx(model.AuditLog{Module: "cross_auth", Action: "anchor",
            Result: "FAIL", Message: err.Error()})
        response.InternalError(c, "anchor failed"); return
    }

    // 4. 更新 session 状态
    session.Status = "VERIFIED"
    session.VerifiedAt = &now
    session.ExpiresAt = &exp
    session.ApprovedBy = c.GetString("username")
    session.TokenJSON = string(tokenJSON)
    h.DB.Save(&session)

    // 5. 写 chain_anchor + audit_log
    h.DB.Create(&model.ChainAnchor{
        BizType: "cross_auth", BizRef: session.RequestID, Digest: digest,
        TxHash: anchor.TxHash, BlockHeight: anchor.BlockHeight,
    })
    h.auditEx(model.AuditLog{
        Module: "cross_auth", Action: "approve",
        Operator: c.GetString("username"), Result: "OK",
        Contract: "anchorcc", Method: "AnchorRecord",
        SubjectDID: session.DeviceDID, TxHash: anchor.TxHash,
        BlockHeight: anchor.BlockHeight,
    })

    response.OK(c, gin.H{
        "status":      "VERIFIED",
        "token":       tokenObj,
        "txHash":      anchor.TxHash,
        "blockHeight": anchor.BlockHeight,
        "expiresAt":   exp,
    })
}
```

### 5.5 实现原理与设计要点
- **三段拆开的必要性**：单段需要客户端同时持有 challenge 和 credential 才能完成 → 但 challenge 是服务端临时生成的，因此必须先 request 拿 challenge → verify 提交签名 → 审批锁定。三段保证了交互完整性
- **二次预言机校验**：从 Stage1（用户开始申请）到 Stage3（管理员审批）可能间隔几分钟，期间设备状态可能恶化（离线/告警），二次校验保证授权时刻设备依然可信
- **token 上链不是 token 本身，是 token 的 SHA256 摘要**：链上只存 digest，对应原文 tokenJSON 在 session.token_json 字段，客户端拿到完整 token + TxHash → 任何时刻可在链上 VerifyDigest 反查
- **token TTL**：默认 1800 秒（30 分钟），可在 request 时调整

### 5.6 答辩追问
- **「Stage1 用 challenge-response 而不是密码？」** challenge 是服务端生成的一次性随机字符串，签名 = sha256(challenge:credential)，攻击者即使截获过去某次的签名也无法重放（challenge 每次不同）
- **「如果 token 被截获呢？」** ① token 有 TTL（30 分钟自动失效）② 管理员可主动 `cross/revoke` 撤销并上链留证 ③ 任何受保护操作都要带 X-Device-DID 等 header，攻击者拿到 token JSON 仍要伪造 header — 不过这是当前实现的弱点，论文 §结论 已承认需要进一步加密 token

## 6. 预言机决策 `checkOracleForAuth`

**位置**：`backend/internal/api/handlers.go:2105`

**职责**：跨域认证前置校验。三条联合判定，任一失败即拒绝。

### 6.1 完整代码

```go
func (h *Handler) checkOracleForAuth(deviceDID string) (bool, string, gin.H) {
    threshold   := h.getOracleThreshold()              // 来自 system_settings.oracle_threshold，默认 3
    activeNodes := h.activeOracleNodes()               // COUNT(OracleNode WHERE status='ACTIVE')
    state, err  := h.latestOracleState(deviceDID)      // SELECT * FROM device_state_updates WHERE ... ORDER BY id DESC LIMIT 1

    if err != nil {
        return false, "missing oracle state", gin.H{"threshold": threshold, "activeNodes": activeNodes, "state": nil}
    }

    ageSec := int(time.Since(state.CreatedAt).Seconds())
    allowed := true
    reason := "ok"

    // 条件 ①：活跃节点数 ≥ 门限
    if activeNodes < int64(threshold) {
        allowed = false
        reason = "active oracle nodes below threshold"
    }

    // 条件 ②：状态新鲜度 ≤ 600 秒
    if allowed && ageSec > 600 {
        allowed = false
        reason = "oracle state expired"
    }

    // 条件 ③：状态 TRUSTED 且 score ≥ 70
    if allowed && (strings.ToUpper(state.StateLabel) != "TRUSTED" || state.Score < 70) {
        allowed = false
        reason = "oracle state not trusted"
    }

    return allowed, reason, gin.H{
        "threshold":    threshold,
        "activeNodes":  activeNodes,
        "stateLabel":   state.StateLabel,
        "score":        state.Score,
        "severity":     state.Severity,
        "message":      state.Message,
        "lastReportAt": state.CreatedAt,
        "ageSec":       ageSec,
    }
}
```

### 6.2 三条判定的设计原理

| 条件 | 含义 | 默认值 | 论文出处 |
|---|---|---|---|
| 活跃节点 ≥ 门限 | "联盟一致"前提：至少 N 个 oracle 节点同时在线 | 3 | §2.4 / §4.4 |
| 状态新鲜度 ≤ 600s | 防止用历史快照糊弄；设备状态是动态的 | 600 秒 | §4.4 |
| 状态 = TRUSTED 且 score ≥ 70 | 业务可信门槛 | 70 分 | §4.4 |

### 6.3 答辩追问
- **「为什么是 70 分？」** 评分模型 = 在线 40 + 固件 30 + 证书 30。70 分等价于"在线 + 固件证书任一有效"或"在线 + 至少一项合规"，低于 70 则核心条件不满足
- **「门限默认 3 怎么定的？」** 系统理论最小门限是 1，但单节点退化为中心化；3 是"奇数 + 投票容错 + 工程简化"的工业经验值（参考 Raft / PBFT 共识下限）
- **「checkOracleForAuth 在三段式哪几步调用？」** 至少 Stage1（发起前置校验）和 Stage3（审批前再次校验）两处，受保护操作中可选

## 7. 预言机评分模型 `oracle/simulator.go`

**位置**：`backend/internal/oracle/simulator.go`

**职责**：把链外信号（在线/固件/证书）量化成 0-100 分。

### 7.1 单节点 baseline 评分

```go
type StatusReport struct {
    DeviceDID     string
    Online        bool
    FirmwareValid bool
    CertValid     bool
    Score         int
}

func Simulate(deviceDID string) StatusReport {
    online := mrand.Intn(100) >= 5    // 95% 在线
    fw     := mrand.Intn(100) >= 10   // 90% 固件有效
    cert   := mrand.Intn(100) >= 8    // 92% 证书有效

    score := 0
    if online { score += 40 }
    if fw     { score += 30 }
    if cert   { score += 30 }

    return StatusReport{
        DeviceDID: deviceDID, Online: online,
        FirmwareValid: fw, CertValid: cert, Score: score,
    }
}
```

### 7.2 多节点变异（per-node noise，让聚合更真实）

```go
// 每个 oracle 节点独立观察同一设备，结果应该接近但允许小差异。
func SimulateForNode(base StatusReport, nodeName string, noiseRate int) StatusReport {
    out := base
    flip := func() bool { return mrand.Intn(100) < noiseRate }
    if flip() { out.Online        = !out.Online }
    if flip() { out.FirmwareValid = !out.FirmwareValid }
    if flip() { out.CertValid     = !out.CertValid }

    out.Score = 0
    if out.Online        { out.Score += 40 }
    if out.FirmwareValid { out.Score += 30 }
    if out.CertValid     { out.Score += 30 }
    out.Score += mrand.Intn(7) - 3   // ±3 抖动

    return clampScore(out)
}

func FakeSign(nodeName string, report StatusReport) string {
    salt := make([]byte, 8)
    rand.Read(salt)
    payload := fmt.Sprintf("%s|%s|%t|%t|%t|%d|%x",
        nodeName, report.DeviceDID, report.Online, report.FirmwareValid,
        report.CertValid, report.Score, salt)
    sum := sha256.Sum256([]byte(payload))
    return hex.EncodeToString(sum[:])
}
```

### 7.3 多节点门限聚合 `oracle_aggregator.go`

完整聚合流程（**真实的多节点投票**）：

```
1. 拉取所有 ACTIVE OracleNode 列表
2. 对每个节点：用 SimulateForNode(base, nodeName, noiseRate=5) 生成本节点观察值
3. 每个节点输出 (online, fw, cert, score) + 假签名（demo 用）→ 写 OracleSubmission 表
4. 投票聚合：
   - online / fw / cert 三个 bool → 多数票胜出
   - score → 中位数（去抖动）
5. 当 N(参与节点) ≥ threshold 且形成多数派 → 写 device_state_update + 上链 anchorcc.AnchorRecord
6. 否则 → 写 PENDING 状态，等待更多上报
```

### 7.4 评分模型可调点

| 参数 | 当前值 | 修改方式 |
|---|---|---|
| 门限阈值 | 默认 3 | 前端"系统管理"页面（实时生效） |
| OracleNode 列表 | 数据库 | 前端"预言机节点注册" |
| score ≥ 70 阈值 | 硬编码 | 改 `handlers.go` |
| 600s 新鲜度 | 硬编码 | 改 `handlers.go::checkOracleForAuth` |
| 评分权重 40/30/30 | 硬编码 | 改 `oracle/simulator.go::Simulate` |

### 7.5 答辩追问（**最高风险问题**）

**Q：「`mrand.Intn(100) >= 5` 这就是个伪随机数生成器，怎么算预言机？」**

**A**：这是教学/演示用的占位实现，生产环境需要替换成真实数据源（SNMP 探针、固件 hash 校验、CRL 证书撤销列表查询）。**但预言机的核心机制**——多节点采集 + 门限聚合 + 链上锚定——在系统设计层是真实存在的：
- `oracle_submissions` 表保留每节点独立上报
- `checkOracleForAuth` 真的强制门限阈值（节点数 / 新鲜度 / 评分）
- 每次 oracle_report 真的调 `anchorcc.AnchorRecord` 上链留证

**"模拟器只换数据源不需重构架构"是本设计的工程优势。**

**Q：「能让预言机真分布式吗？」**

**A**：现在 OracleNode 表只记节点公钥，实际上报是单进程同步调用。改造路径：
1. 每个 oracle 节点作为独立进程跑（不同机器）
2. 通过 HTTPS 接口上报 `(DeviceDID, signedReport)` 到后端
3. 后端按 nodeId 校签 + 按门限聚合 → 真正的"分布式预言机"

### 8.2 JWTAuth（jwt.go）

```go
func JWTAuth(secret string) gin.HandlerFunc {
    return func(c *gin.Context) {
        tokenStr := strings.TrimPrefix(c.GetHeader("Authorization"), "Bearer ")
        if tokenStr == "" { c.AbortWithStatusJSON(401, ...); return }

        claims := &AuthClaims{}
        parsed, err := jwt.ParseWithClaims(tokenStr, claims, func(t *jwt.Token) (any, error) {
            return []byte(secret), nil
        })
        if err != nil || !parsed.Valid { c.AbortWithStatusJSON(401, "invalid token"); return }

        c.Set("userId",     claims.UserID)
        c.Set("username",   claims.Username)
        c.Set("role",       claims.Role)
        c.Set("domainCode", claims.DomainCode)
        c.Next()
    }
}
```

### 8.3 EnsureUserValid（user_guard.go）

```go
// 二次校验：即使 token 未过期，也要确保数据库里用户还有效
func EnsureUserValid(db *gorm.DB) gin.HandlerFunc {
    return func(c *gin.Context) {
        userID := c.GetUint("userId")
        var u model.User
        if err := db.First(&u, userID).Error; err != nil {
            c.AbortWithStatusJSON(401, "user invalidated"); return
        }
        // 重新覆盖 ctx 字段，token 中的角色可能已被吊销
        c.Set("userId", u.ID); c.Set("role", u.Role); c.Set("domainCode", u.DomainCode)
        c.Next()
    }
}
```

### 8.4 答辩追问
- **「为什么 JWTAuth 之后还要 EnsureUserValid？」** JWT 是无状态的，签发后只看 secret 验签。若管理员吊销了某用户但 token 未过期，单靠 JWT 仍能通过；EnsureUserValid 强制二次查库确保用户仍存在 + 角色未变
- **「JWT 过期时间多久？」** 12 小时（见 `handlers.go::Login` 里 `"exp": time.Now().Add(12 * time.Hour).Unix()`）

## 10. 一句话答辩压舱石

> 本系统的核心思想是「**链下业务库 + 链上锚定**」双层信任：链下处理高频、低敏的读写，链上锚定关键事件摘要做不可篡改证据。Hyperledger Fabric 联盟链作为链上层，单一链码 `anchorcc` 提供 AnchorRecord / QueryAnchor / VerifyDigest 三个接口；后端通过 fabric-gateway SDK 调用，每笔上链都经过 **Org1+Org2 双组织背书 + Raft 排序 + 双方提交 commit**。
>
> 跨域认证三段式（Request → Verify → Approve）串接**信任策略 + 预言机评分 + 链上锚定**，跨域门禁中间件对受保护操作做 4 重校验。
>
> 预言机用 **OracleNode 表 + 门限阈值**实现「工程上的最小可信集」，每次状态上报通过 `anchorcc.AnchorRecord` 上链留证；checkOracleForAuth 用三条联合判定（活跃节点≥门限 + 新鲜度≤600s + 状态TRUSTED且评分≥70）作为跨域决策依据。
